# ADR 0013：故障注入——在真实多进程部署上验证恢复路径

- 状态：已采纳
- 代码：`faults/`（`proxy.py` 故障代理、`infra.py` Postgres/Redis、`cluster.py` 进程、`model.py` 受控模型、`clients.py` 观众客户端、`invariants.py` 不变量、`run.py` 场景、`__main__.py` 命令行）
- 命令：`make faults`（全部场景，约 3 分钟）、`make faults-quick`（CI 子集，约 80 秒）、`python -m werewolf_harness.faults run --scenario node_kill --games 3`
- 报告：`faults/report.md` + `faults/report.json`，`faults/report-quick.md`
- 回归测试：`tests/integration/test_fault_fixes.py`
- 相关：ADR 0002（提交顺序）、0004（租约与 fencing）、0005（Redis Streams）、0008（录制回放）、0009（流式草稿）

## 背景

恢复逻辑之前只在两种环境里验证过：单进程集成测试（同一个事件循环里模拟崩溃），和 `scripts/chaos_demo.py`（杀一次节点）。真实部署是多个独立进程，经网络连接 Postgres 和 Redis。以下几类故障，在单进程测试里根本触发不了：

- worker 进程在回合中途死掉；
- Redis 重启后数据全丢（没开持久化）；
- Postgres 在事务进行中崩溃；
- 连接被重置、网络分区；
- 旧 owner 被冻住，醒来时对局已经被别的节点接管。

## 决定

### 1. 用真实进程跑

一次运行会起这些进程：

- Postgres 和 Redis 各一个，端口随机；
- 2 个 API 节点（uvicorn），2 个模型 worker（Redis Streams 消费者），都是独立进程，执行器用 `AGENT_EXECUTOR=streams`。

所有服务到 Postgres 和 Redis 的连接，都经过自写的 asyncio TCP 故障代理（`faults/proxy.py`）。没有用 toxiproxy。代理能做这些：

- 加延迟和抖动；
- 模拟丢包：TCP 里字节不会真丢，丢包的代价是重传，所以按概率给分段加 200–600 ms 延迟；
- 分区：连接保持，但不转发任何数据；
- 用 RST 重置全部连接；
- 拒绝新连接。

检查不变量用的连接直连数据库，不经过代理。

| | 本机（默认） | CI |
|---|---|---|
| Postgres | 自己 `initdb` 一个临时集群；“重启”是 `pg_ctl stop -m immediate`，等于崩溃，启动时走 WAL 恢复 | 共享服务容器，重启不了；用代理模拟：拒绝新连接 + 重置所有连接 |
| Redis | 自己起 `redis-server --save "" --appendonly no`；“重启”是 SIGKILL 后起一个空的 | 共享；代理拒绝连接 + 重置 + `FLUSHDB` |

时钟调快，让一次故障几秒内演完：

| 参数 | 值 |
|---|---|
| 租约 | 3 s |
| 续约间隔 | 0.5 s |
| 恢复扫描间隔 | 0.5 s |
| 回合期限 | 25 s |
| 任务认领空闲阈值 | 3 s |

### 2. 座位：确定、免费、可控

座位模型是 `faults-mock`，即 `MockClient` 加上两样东西。只有设置了 `FAULTS_CONTROL` 时才会提供这个模型。

- **控制文件**（JSON）：harness 在场景进行中原子地改写它，比如 `{"error_rate": 0.5}`。每个进程最多 100 ms 读一次，所以 API 节点和 worker 会在同一时刻进入同一个故障窗口。
- **调用日志**（JSONL，各进程以 `O_APPEND` 方式写入同一个文件）：每次模型调用记一行，包括局、座位、提问时的版本号、任务、ReAct 步号、开始时间。网关把这些上下文交给原始客户端（`bind_call`，只有测试座位实现了它）。

决策按种子确定，发言是流式的，每局约 20 秒，长度刚好够故障落在回合中间、发言中间。

### 3. 场景

| 场景 | 注入方式 |
|---|---|
| `worker_kill` | 有草稿正在流式输出时 kill -9 一个 worker，2 s 后重启；同一局里做两次 |
| `node_kill` | kill -9 持有对局最多的 API 节点；另一节点等租约过期后接管 |
| `redis_restart` | Redis 消失后带着空数据回来；做两次 |
| `pg_restart` | 提交正在进行时 Postgres 崩溃；第一次停 2 s，第二次停 12 s（超过 actor 的提交重试窗口，约 9 s） |
| `model_faults` | 依次进入四个窗口：50% 调用 503；50% 调用 1 s 后超时；100% 报错；每次调用慢 2.5 s |
| `network` | 链路延迟 150±100 ms；20% 分段重传；分区 2.5 s；最后重置全部连接 |
| `dup_zombie` | 把最近的模型任务重复投递 24 次；把 owner SIGSTOP 冻住，超过租约，等别的节点接管后再 SIGCONT 唤醒 |

每个场景默认同时跑 2 局。`--quick` 只跑前两个、`model_faults` 和 `dup_zombie`，每个场景 1 局，故障窗口减半。

### 4. 每个场景后自动检查的不变量

| 不变量 | 怎么查 |
|---|---|
| 日志连续无重复 | 每局 `journal.seq` 恰好是 0..n-1 |
| fencing 单调 | 运行期间每 100 ms 采样一次 `games.fencing_token`，不允许下降 |
| 已提交回合不再调模型 | 在调用日志里取每个回合的第一步调用（`step == 0`），它的开始时间不能晚于这个回合在 journal 里的提交时间 |
| 客户端草稿闭合 | 每局一个真实 WebSocket 客户端、一个 SSE 客户端，行为和 `web/app.js` 一致：带游标重连，收到 4404 改为轮询。客户端看到的内容灌进 `DraftMirror`，最后看到的每段草稿要么提交、且文字与 journal 一字不差，要么被撤回；事件序号不跳；能收到结束事件 |
| 每局终结 | 要么打完，要么以 aborted/crashed 明确报错，不允许卡住 |
| 重放一致 | 用 (seed, journal) 重建已结束的局，终局和实时一致 |
| 座位记忆对齐 | 每一行 `agent_state` 都对应一行由该座位提交的 journal |

输出是“场景 × 不变量”的 ✓/✗ 矩阵和耗时，外加步数、兜底数、接管数，写到 `faults/report.md` 和 JSON。只要有一个 ✗，就以非零状态退出。

## 发现的问题

下面的问题里，1–5、7、9 是跑 harness 跑出来的（3 和 9 是修完其它问题后的全量运行里才暴露的），6 和 8 是写 harness 时读代码发现的。每一个都有回归测试，并且确认它在修复前的代码上会失败。

| # | 现象（场景） | 机制 | 处理 |
|---|---|---|---|
| 1 | Redis 一重启，两个 worker 进程全部退出，对局卡死（`redis_restart`、`network`） | `Worker.run` 里 `XREADGROUP` 的连接异常没有被接住；Redis 空着回来后还会报 NOGROUP | 读任务出错时退避重试，并重建消费组；`_handle` 出错时只记日志，任务不 ACK，留给别的 worker 重领 |
| 2 | 节点失去对局后（租约丢失、被 fence），连在它上面的 WebSocket 客户端一直挂着，收不到后续（`dup_zombie`、`redis_restart`） | 推送循环不检查 actor 是否已停止 | actor 因为“对局去了别处”而停止时，用 4409 关闭连接，客户端带游标重连到新 owner |
| 3 | 客户端恰好在节点放手的那一刻连上，要白等一个心跳周期（25 s）；这期间对局在别处打完，客户端就收不到结局（`pg_restart`，偶发） | 停止的 actor 不会再触发通知，等待只能等到超时 | WebSocket 和 SSE 都改成：actor 已停止就不再等待，把剩下的内容发完后立即结束 |
| 4 | worker 被杀后，它手上的任务要等满回合期限才被别人领走，回合总是兜底（`worker_kill`：每次被杀产生 1 次兜底） | 认领空闲阈值等于回合期限；`XAUTOCLAIM` 只看任务空闲了多久，看不出 worker 还活不活着 | worker 每隔“阈值的三分之一”用 `XCLAIM … JUSTID` 刷新自己在跑的任务；阈值改为单独配置（`CLAIM_IDLE_MS`，默认 15 s）。这样阈值衡量的是 worker 死了多久，而不是回合要跑多久 |
| 5 | 节点投任务时 Redis 正好断开，任务静默丢失，回合等到期限后兜底（`redis_restart`、`network`） | `XADD` 是用 `create_task` 发出去就不管，失败只出现在“Task exception was never retrieved”日志里 | 退避重试，直到发出去，或者这个任务被取消；worker 回写结果和 ACK 也加了重试 |
| 6 | 被取消的任务一直占着这局在队列里的名额（每局 4 个），直到 worker 回复；Redis 把任务弄丢时，回复永远不会来 | 名额要等回复到了才释放 | 取消时立即释放名额 |
| 7 | 在线服务里，唯一模型的一次 503 就让回合直接兜底（`model_faults`：88 个回合里 61 个兜底） | `table.py` 的注释说“网关已经做过退避”，于是把座位层的重试关了；可网关对每个模型只试一次、不退避 | 座位层重新启用重试：最多 2 次，退避 1 s、2 s |
| 8 | 在 streams 模式下，worker 进程的模型调用记录从来没写进 `llm_calls`，看板和成本统计漏掉了全部 worker 调用 | 只有 API 节点在定时把调用记录写进数据库 | worker 也每秒写一次，退出前再写一次 |
| 9 | Redis 刚重启的约 1 秒里，所有 `/api/` 请求都返回 500 | 按 IP 限流的中间件拿到了连接池里一条已经断开的连接，抛出 `RuntimeError` | 限流在 Redis 不可用时放行请求，并计数 |

## 结果

“修复前”是 harness 第一版的运行结果，“修复后”见 `faults/report.md`。两次都是 7 个场景、每个场景 2 局，本机自起 Postgres 和 Redis。

| 场景 | 修复前：失败的不变量 / 用时 / 兜底 | 修复后 |
|---|---|---|
| worker 回合中被 kill -9 | 无 / 65.1 s / 2 | 全 ✓ / 23.0 s / 0 |
| owner 节点被 kill -9 | 无 / 16.6 s / 0 | 全 ✓ / 15.0 s / 0；接管用时约 3 s（租约 3 s） |
| Redis 重启 | 客户端草稿闭合、每局终结（1 局卡死） / 150 s / 8 | 全 ✓ / 19.7 s / 0 |
| Postgres 崩溃重启 | 无 / 74.6 s / 3 | 全 ✓ / 39.2 s / 0 |
| 模型故障窗口 | 无 / 19.7 s / **61 / 88 步** | 全 ✓ / 27.2 s / 0 / 51 步 |
| 网络故障 | 每局终结（2 局卡死） / 150 s / 10 | 全 ✓ / 31.3 s / 0 |
| 重复投递 + 旧 owner 醒来 | 客户端草稿闭合 / 115.7 s / 5 | 全 ✓ / 17.2 s / 0 |
| **全量** | 3 个场景失败，607 s | **全部通过，180 s** |

几点说明：

- 修复前，“模型故障窗口”场景其实是全 ✓。但它只用 19.7 s 就打完了，因为 61 个回合都是兜底：3 秒的 100% 故障，把剩下的整局在几秒内用默认动作走完了。不变量全部成立，不代表服务行为是对的，所以报告里同时给出兜底数。
- 重复投递的 24 个任务和醒来的旧 owner，在两个版本里都没有造成重复写入。这条路径（版本号去重、fencing 拒绝）本来就是对的。

## 局限

- 所有进程都在同一台机器上，时钟相同。“已提交回合不再调模型”这一条依赖同一个时钟，比较的是 journal 的 `created_at`（事务开始时间）和调用开始时间，允许 50 ms 误差。
- 座位是 mock，不是真实模型，所以覆盖的是协议层和恢复路径，测不了模型本身的行为。真实模型的录像回放见 ADR 0008。
- CI 里 Postgres/Redis 的“重启”是用代理模拟的，模拟不了 WAL 恢复，也模拟不了 Redis 进程真的死掉。全量场景要在本机跑。
- 没有覆盖：磁盘写满、时钟漂移、Caddy 这一层、浏览器里的 `app.js` 本身（观众客户端只是按它的协议实现了一遍）。
- 每个场景只跑 2 局。报告里的数字说明“这些路径走得通”，不是概率意义上的可靠性估计。
