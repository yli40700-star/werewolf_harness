# ADR 0011：过载保护——在门口排队，进行中的牌局不让路

- 状态：已采纳
- 代码：`app/runtime/load.py`（过载信号）、`app/runtime/admission.py`（准入）、`app/runtime/agents.py`（LocalExecutor 公平调度）、`app/llm/queue.py`（Streams 每局上限、负载采样）、`app/api/main.py`（202 / 503 / `/api/load`）、`web/app.js`（排队提示、负载徽章）
- 压测：`python -m werewolf_harness.scripts.bench_overload`（约 100 秒，需要本机 Postgres + Redis）

## 问题

模型供应商一变慢，每个回合都变长，worker 池被占满，任务开始排队。这时如果新桌照开不误，新桌的回合和老桌的回合排在同一个队里，所有牌局一起变慢，直到一起卡死。玩家感受到的是：本来在顺利进行的一局，因为别人在开新桌，突然每一步都要等很久。

要的效果：**进行中的牌局保持原来的延迟（只受供应商本身变慢的影响），新桌等待或被拒绝。**

## 决策

### 1. 过载信号（`load.py`）

每个 `load_tick_s`（0.5 秒）以及每次开桌请求时采样一次执行器和网关：

| 输入 | 来源 |
|---|---|
| 每条 lane 的排队任务数 | LocalExecutor 自己的等待队列；Streams 用消费组的 `lag`，加上节点上被每局上限扣住的任务（`held`） |
| 最老排队任务的等待时间 | 同上（Streams 取 last-delivered-id 之后第一条的 id 时间戳） |
| 在途数 / 容量 | 线程池大小；Streams 是 PEL 里的 pending 数 / 各 worker 在 `llm:workers` 里报的并发之和 |
| 最近的回合耗时、在途任务的平均已运行时间 | 执行器 |
| 最近的单次模型调用延迟 | 网关 `Hub.latency`（每次成功或超时的调用记一笔） |

合成一个压力值（1.0 = 到线）：

```
pressure = max( demand / demand_per_slot,                       demand = (在途 + 排队) / 容量，3 秒 EWMA
                games × per_game / 容量 / demand_per_slot,        per_game = 每局平均要占的位置，20 秒 EWMA
                max(最老等待, 预期等待) / wait_s,                   预期等待 = 排队数 × 回合耗时 / 容量
                单次调用 p50 / latency_ms )                        回合耗时 = max(最近完成回合 p50, 2 × 在途平均已运行时间)
```

为什么是这几项：

- **demand**：池子满了以后再开新桌不会增加吞吐（吞吐就是池子的位置数），只会把同样的吞吐分给更多牌局，每局都变慢。所以「想占位置的任务 = 位置数」就是新桌开始拖累老桌的点。供应商变慢时，它通过这一项起作用：每局要多花 10 倍时间才结束，同样的到达速率下同时在跑的局数就多 10 倍（Little 定律）。
- **games × per_game**：同一件事往前看。刚开的局夜里只问一两个座位，8 人投票要到第一天白天才来；只看当下 demand 会在信号反应过来之前放进一大批新局。按平均权重计每一局，补上这个滞后。
- **等待**：这是玩家直接感受到的（回合还没开始算）。预期等待用在途任务的已运行时间估计回合耗时，供应商一变慢立刻就能看到，不用等慢回合跑完。新局第一回合本来就被安排在后面（见下文），它的等待不算进「最老等待」，否则「让新局等」本身会把节点一直卡在过载里。
- **单次延迟**：供应商慢到即使不排队每回合也超预算时兜底。

各 lane 的排队数和利用率另外作为指标导出（`wh_llm_queue_depth{lane}`、`/api/load`），它们是 demand 的组成部分。

**迟滞**：压力 ≥ 1.0 立刻进入过载；压力 ≤ 0.7 连续 `hold_s`（3 秒）才退出。一次投票同时问 8 个座位，压力会瞬间冲高再回落，没有迟滞准入会在「全放」和「全不放」之间来回跳。指标：`wh_load_pressure`、`wh_overloaded`。

延迟窗口按「最近 16 个」而不是「最近 N 秒」统计：变慢之后，变慢前发出的快请求还在大批返回，而每个慢请求要 10 倍时间才回来，按时间窗的中位数会在旧速度上停留很多秒。

### 2. 准入控制（`admission.py`，`POST /api/games`）

```
decide(过载?, 排队长度, 上限, 在跑局数) →
    admit   不过载、队空、未到 max_active_games，且不在「试探间隔」内   → 201，立刻开局
    queue   否则，队没满                                             → 202 {state:"queued", queue:{position, eta_s}}
    reject  队满（max_queued_games，默认 50）                         → 503 + Retry-After
```

- **严格 FIFO**：只要有人在排，后来的就排在后面，即使此刻节点恰好不忙——否则刷新得巧的人能插队。
- **排队的局是真的行**：Postgres 里 state='queued'（迁移 `h1_queued_state` 放开了 CHECK），不拿租约，恢复扫描不会接管它。节点重启后按创建顺序把自己的排队局放回队里。
- **自动开局**：每个 tick，不过载且队不空就开队头一局（每 tick 一局，给信号留出看到它的时间）。
- **忙碌带里的慢启动**：压力在 0.7 和 1.0 之间（busy）时，`admission_probe_s`（5 秒）内最多开一局，直接开或从队里开都算。原因同上：新局的真实分量要一分钟后才显现，没有这一条，节点会在信号越过 1.0 之前一口气吃下一整批。
- **ETA**：每局结束会腾出一个位置，局的离开速率约为 `在跑局数 / 平均局长`，所以第 N 位约等 `N × 平均局长 / 在跑局数`。平均局长是本节点结束局的 EWMA（初值 120 秒）。这是给人看的提示，不是承诺。Retry-After = 队尾的 ETA，夹在 [5, 600] 秒。
- **进行中的局从不暂停**：保护只在门口。`create()`（测试、压测、导入存档）和恢复接管不经过准入。
- `/readyz` 在过载时仍然返回 ready：在跑的局需要这个节点，只是新局要等。

### 3. 优先级与每局公平

lane 仍是严格优先（human > online > offline）。lane 内部新增两条：

**进行中的局先于新局的第一回合。** LocalExecutor 的排序键是 `(lane, 是否新局第一回合, 该局在跑任务数, 该局上次被服务的时刻, 到达序号)`。新局第一回合（version == 0）排在所有进行中局的任务后面；等满 `new_grace_s`（10 秒）后不再让路，避免饿死。

**一局不能靠并行提问饿死别人。** 现在投票会同时问 8 个座位，一局一瞬间往队里放 8 个任务；FIFO 下这一局会拿走接下来的 8 个线程，别的局一个发言回合也得等在后面。（ADR 0005 里「一局最多一个未完成回合，所以 FIFO 就是轮转」的前提已经不成立。）

两种做法都考虑了：

| | actor 里给每局设并发上限 | 执行器里做每局公平排队 |
|---|---|---|
| 没有竞争时 | 浪费：一局单独在节点上也只能用 k 个线程，投票变慢 | 工作保持（work-conserving）：一局可以用满 8 个线程 |
| 有竞争时 | 每局最多 k 个，近似公平 | 选「在跑任务最少、最久没被服务」的局，max-min 公平 |
| 需要什么 | 只要 actor 改一行 | 执行器得拥有自己的队列 |

**选择：LocalExecutor 用公平排队**（它拥有自己的队列，`ThreadPoolExecutor` 自带的 FIFO 不再使用），因为它只在真有竞争时才约束，空闲时不损失并行提问带来的速度。`per_game_cap` 参数保留一个可选的硬上限（默认关）。

**Redis Streams 执行器用每局上限**（`per_game_asks`，默认 4）。流是所有节点共享的 FIFO，不能重排；能做的只有在源头限流：一局在流里最多 k 个任务，其余扣在节点上，等这一局的结果回来再放出去。每局最多占 k 个位置的 FIFO，相当于误差在 k 以内的轮转。为了让名额一定能还回来，worker 丢弃过期任务时现在会回一条 `stale` 回执（以前什么都不回）；死信或丢失的回执靠 `agent_timeout_s + 5` 秒的 TTL 兜底。Streams 模式下「进行中优先于新局」只靠准入控制实现，不在队列里排。

### 4. 大厅界面

- 页头的负载徽章：负载正常 / 负载偏高 / 过载 · 新桌排队（每 2.5 秒拉一次 `/api/load`）。
- 开桌返回 202 时停在大厅，显示「当前排队中：第 N 位，预计 X 秒」，轮询 `/api/games/{id}/queue`，开局后自动进桌；返回 503 时提示多少秒后再试。
- 列表里排队的桌显示「排队中 · 第 N 位」，按钮不可点。

## 测量

`scripts/bench_overload.py`：4 局 8 人局（全部模拟模型，每次调用 0.2 秒）先跑起来；3 秒后供应商变慢 10 倍（每次调用 2 秒，`sim.CONTROL`）；之后 20 秒里每秒请求一局新桌，共 20 局；再恢复 14 秒。16 个 worker 槽，排队上限 10。「回合延迟」= 模型任务提交到结果送回 actor，只算变慢之后提交的；到结束还没回来的按已等待时间计入（下界）。数字来自模拟供应商（SimClient 延迟 + MockClient 决策）。

| 指标（模拟供应商） | 没有新桌（参照） | 保护关 | 保护开 |
|---|---|---|---|
| 老局：回合 p50（秒） | 4.94 | 6.71 | 5.41 |
| 老局：回合 p95（秒） | 8.16 | 6.84* | 8.28 |
| 老局：结束时仍未返回的回合 | 4 | 11 | 6 |
| 老局：每秒提交步数（整个变慢阶段） | 1.15 | 0.80 | 1.10 |
| 老局：每秒提交步数（后半段，队列已积起来） | 1.30 | 0.60 | 1.20 |
| 新桌请求 | 0 | 20 | 20 |
| 　立刻开局 | 0 | 20 | 7 |
| 　排队 | 0 | 0 | 11 |
| 　拒绝（503） | 0 | 0 | 2 |
| 　排队后开局 | — | — | 1（等了 4.3 秒） |
| 　排队时给出的 ETA p50 | — | — | 55 秒 |
| 状态切换次数 | 0 | 1 | 1 |

\* 保护关的 p95 偏低是截断造成的：11 个回合到结束都没回来，只按已等的时间计入。看后半段的提交速率更清楚：保护关时老局的推进速度掉到参照的 46%，保护开时是 92%。

没有做到的：供应商恢复后的 14 秒里只开了排在队头的那一局。这是对的——同时在跑的局仍占满池子（闭环系统里需求不随供应商速度下降），名额要等局结束才腾出来，而这个窗口里没有局结束。排队局按 FIFO 自动开局由集成测试覆盖（`tests/integration/test_backpressure.py`）。

## 后果

- 过载时新用户等，而不是所有人一起等。排队的局在大厅里能看到位置和预计时间。
- 准入是反应式的，有一两个 tick 的滞后；慢启动和 per_game 投影把这个滞后造成的超额压到几局以内（上表：20 个请求里放进 7 个）。
- 排队局属于创建它的节点；那个节点永久消失时，它的排队局会一直是 queued，需要人工清理或以后加「接管别人的排队局」。
- 阈值（`overload_*`、`admission_probe_s`、`max_queued_games`、`per_game_asks`）都在 `Settings` 里，可以按部署调。
- 复现 0.3 秒 → 3 秒的跳变：`python -m werewolf_harness.scripts.bench_overload --fast-ms 300 --slow-ms 3000 --slow 40`（回合更长，所以变慢阶段要拉长才看得到同样多的回合，跑得也更久）。worker 进程可以用环境变量 `SIM_MEDIAN_MS` / `SIM_LATENCY_SCALE` 直接以慢速启动。接真实供应商时看 `/api/load` 以及 `wh_load_pressure`、`wh_overloaded`、`wh_admission_wait_s`。
