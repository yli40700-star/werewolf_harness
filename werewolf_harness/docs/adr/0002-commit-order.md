# ADR 0002：每一步的提交顺序（journal-first）

- 状态：已采纳
- 代码：`GameActor._commit` / `_commit_inner`

## 顺序

```
① INSERT journal(game_id, seq, …) + agent_state   —— 同一个事务，带 fencing token
② 应用到内存里的世界，version += 1
③ 发布事件（WebSocket / SSE）
```

## 各个崩溃点会发生什么

| 崩在哪 | 现象 | 恢复后 |
|---|---|---|
| ① 之前 | 这一步没发生 | 新 owner 重放到上一步，重新问这个回合（这一步的模型调用会再发一次，最多一次） |
| ① 事务中 | 事务回滚，等同于「① 之前」 | 同上 |
| ① 之后、② 之前 | 数据库里有，内存里没有 | 重放时包括这一行，这一步算发生过 |
| ② 之后、③ 之前 | 客户端没收到事件 | 事件是 journal 的派生物，重放时重新生成；客户端带 `last_seq` 重连，补发缺的部分 |
| ③ 之后 | 正常 | — |

## 为什么不是「先改内存再写库」

先改内存再写库，如果写库失败，内存里的世界就比数据库多走了一步。此时要么回滚内存（引擎不支持撤销），要么让两份状态分叉。以 journal 为准时，写库失败就不生效，内存永远不会领先于数据库。

## 幂等的三层

1. `journal` 主键 `(game_id, seq)`：同一步只能写一次，并发写只有一个成功（测试：8 个并发写，1 个成功）。
2. `UNIQUE (game_id, request_id)`：客户端重试或双击，只落一次。
3. 模型结果带 `version`：超时后才到的结果、重复投递的结果，actor 直接丢弃。

## 事件序号的稳定性

已提交步骤产生的事件序号，跨重启不变，因为事件由 journal 重放生成。「当前轮到谁」的提示和恢复标记会重新发出，所以恢复前后同一个序号上的内容可能不同。客户端只把事件当作「该拉最新状态了」的信号，不依赖事件内容，这一点不影响正确性。
