# ADR 0005：模型任务队列用 Redis Streams，不用 Kafka

- 状态：已采纳
- 代码：`app/llm/queue.py`

## 需求

模型回合要从游戏循环里拿出去，交给可以独立扩容的 worker。要求：

- 至少投递一次；
- worker 挂了任务不丢；
- 「有人在等」的回合优先；
- 失败太多次的任务要能单独看到。

## 为什么 Redis Streams 够用

| 需求 | Redis Streams 的做法 |
|---|---|
| 至少一次 | 消费组 `XREADGROUP`，处理完才 `XACK`；未确认的消息留在 PEL 里 |
| worker 崩溃 | 其他 worker 用 `XAUTOCLAIM` 认领空闲超过 `claim_idle_ms`（15 s）的消息；活着的 worker 每 5 s 给在跑的任务续一次（ADR 0013） |
| 死信 | 投递次数超过 3 次的，写入 `llm:dead` 并 ACK 掉，同时给原节点的结果流发一条 `dead` 通知，节点立刻重问一次（2026-10-17） |
| 优先级 | 三条流 `llm:jobs:human / online / offline`，worker 按顺序先非阻塞检查高优先级的流 |
| 结果回传 | 按节点分流 `llm:results:{node}` |
| 调用记录 | worker 把每次模型调用的记录批量写进 `llm:calls` 流；每个 API 节点跑一个 `CallRelay`（消费组 `recorders`），写进 Postgres 成功后才 ACK，失败的批次 10 s 后可被任一节点重新认领（2026-10-26） |

Redis 本来就在（租约、限流、在线状态），不用多运维一个组件。量级上：一局约 250 次模型调用，几百桌同时进行也只是每秒几十到几百条消息。

## 任务里带什么（2026-10-26 修订）

可见性判断和局面计算都在 actor 这边。轮到某个座位时，actor 用自己内存里的引擎算出这个座位的视图和动作空间，连同记忆、版本号、座位设置（解析后的模型、强弱路由策略、token 上限、守卫、语言等）一起打包进任务：

- `view`：裁剪过的视图，用 `arena/wire.py` 编码。普通 JSON 会把整数键的字典变成字符串键、把元组变成列表，提示词会因此变化，所以这两种形状单独打了标签，解码后和原视图完全相等。
- `spec`：`ActionSpec.to_dict()`。狼队定战术那条跨参数规则原来是一个闭包，改成了数据（`AssignRule`），拒绝的输入和原来一样。
- `player`：`Table.seat_settings` 给出的座位设置，worker 和进程内路径都用 `app/runtime/seats.py` 的 `build_player` 构造玩家，两边不会走偏。

worker 只拿着包去问模型，查询工具从包里的视图取答案，不连 Postgres，不重放日志，也不需要引擎。提交前的检查不变：actor 重新算视图和动作空间，比对指纹和 spec key，再 `spec.check`。

这样做以前，任务只带 (game, seat, version, task, memory)，worker 每次从 Postgres 读日志重放出局面再生成视图。改的理由：局面本来就在 actor 内存里，再在 worker 重建一遍多一次数据库读，也让 worker 依赖数据库和引擎；改完以后 Redis 和 worker 里只有这个座位能看到的内容。

## 局间公平不需要调度器

（已被 ADR 0011 修订：并行提问以后一局可以同时有 8 个未完成回合，下面的前提不再成立；现在节点给每局在流里的任务数设上限。）

一局在任意时刻最多只有一个未完成的模型回合，因为游戏是回合制的，actor 会等这个回合的结果。所以同一条流里的 FIFO 本身就等于在各局之间轮转，一个「话多」的局不会把别的局饿死。原计划里的「加权公平调度」因此删掉了，只保留优先级分流。

## 重复执行

至少一次意味着同一个任务可能跑两次（worker 在模型答完、ACK 之前挂掉）。接收端靠 `version` 去重：actor 只接受它正在等的那个 version 的结果。actor 不再需要的任务（倒计时到期、对局停止）会被标记成已关闭：节点设置 `llm:closed:{job_id}`（1 h 过期），并在 `llm:cancel` 上广播，让正在跑的 worker 停下。worker 交回答案后也会关闭这个任务。worker 开跑前对这个键做一次 `EXISTS`，已关闭就直接丢弃，不调模型；没赶上的结果回到 actor 时按 version 和视图指纹丢掉。（2026-10-26 以前，这一步是 worker 重放日志、看这个座位的回合是否还开着。）

已知的取舍：节点被 kill -9 时，它还排在队列里、没被领走的任务仍会被执行，答案发到死掉节点的结果流里，花了 token 但影响不了对局；原来的重放检查能在接管节点提交该回合后丢掉它们。

## 什么时候换 Kafka

有多个团队订阅同一批事件，需要长期保留和回放（例如把 journal 事件流给数仓或训练数据管道），或者吞吐到每秒几万条时。
