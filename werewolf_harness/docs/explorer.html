设计札记 · Werewolf Arena

一个多智能体对抗环境该由什么来保证正确

本文记录的是若干设计决定的依据，以及其中两项后来被推翻的论断。它不是使用说明。

§1问题的定位：认知分发，而非流程编排

做多智能体系统时，第一反应是找个编排框架：把流程画成图，节点是智能体，边是流转条件。这套做法在协作型任务里够用——大家目标一致，信息共享，谁先谁后主要是效率问题。

对抗型任务不一样。狼人杀里有一件事是协作型任务里不存在的：不同的参与者对"世界现在是什么样"必须有不同的、且受控的认知。狼知道同伴是谁，预言家知道验过谁，村民什么都不知道，而这三份认知必须来自同一个世界。

于是问题从"怎么编排"变成了"世界是什么样，这件事能有几个说法"。一个典型实现里，它至少有四个说法：引擎里的状态字段是一份，拼提示词时手写的那段描述是一份，校验模型输出时的那段判断是一份，跑完之后统计脚本重新解析日志又是一份。四份各自演化，谁也不保证一致。

能观察到的症状是这样的：提示词告诉模型"你可以救人"，模型照做，执行层拒绝，因为解药已经用掉了——两处各写了一遍规则，改了一处忘了另一处。或者更糟：某一局狼人精准地投出了预言家，没人能说清是推理还是泄露，因为"狼能看到什么"这件事没有唯一的定义点。

§2控制流索引在路径上，还是索引在状态上

在动手之前先确认过这个轮子该不该造。图编排类框架（LangGraph 一类）把控制流表达成图，对抗环境类项目（TextArena 一类）提供的是环境集合、目标是给模型排名。前者的问题不在于表达能力，而在于分支挂在什么上面；后者的问题是把环境当作固定资产，新增环境、替换规则参数、把真人塞进某个座位都要改它的内部。

先说前者，因为那才是结构性的分歧。

分支的索引方式决定规则的复制次数

自动机理论里这组区分早有名字：Mealy 机的输出取决于（当前状态，这条转移），Moore 机的输出只取决于当前状态。图编排的条件边天然是 Mealy 的——路由函数的名字里就带着"从哪个节点来"（route_after_night、route_after_vote）。

这个区分在对抗游戏里立刻变成可数的代价。这套规则里能致死的路径有六条：夜刀、女巫毒、同守同救抵消、白天票出、狼自爆、猎人开枪。而死亡的后果有三条：猎人要开枪、警长要传警徽、够条件的人要留遗言。

Mealy 式的写法里，每一个可能死人的节点后面都要挂一条条件边，而每条边都得把三个后果问一遍。六个来源乘三条后果，是十八处判断；再加第四条后果，要在六个路由函数里各补一遍。更麻烦的是这十八处之间没有任何机制保证一致：把"被女巫毒死的猎人不能开枪"这条改动漏在其中一处，程序不报错，只会打出一局"夜里毒死能开枪、白天票出不能开枪"的怪棋。

Moore 式的写法把分支挪到状态上。六条致死路径全部经过同一个函数 _kill(seat, cause)，它记录死亡，然后由 _queue_deaths 判断三条后果——写一遍。调度函数 _next() 不知道刚才发生了什么，也不需要知道，它只读当前状态：狼死光了吗、有待处理的插入回合吗、现在是什么阶段。夜里被毒死的猎人和白天被票出的猎人走到这里时是同一个状态（_pending_hunter 有值），因此只需要一次判断。六加三，是九处；加第四条后果，改一处。

乘积塌成求和的原因是所有路径在写状态的那一刻汇合了。图编排里没有这个汇合点——状态虽是共享字典，控制流却不共享，所以判断必须在每条出边上重来一遍。

汇合点的代价

这不是免费的。Moore 化意味着把"隐含在控制流里的信息"显式化成状态：_pending_hunter、_pending_badge、_pending_last_words、_settle_to 这些字段之所以存在，纯粹是为了记住"接下来该干什么"——Mealy 机不需要它们，那个信息藏在"程序正走在哪条边上"这个事实里。本质是拿存储换分支数。

更要紧的是，整个论证建立在一个前提上：所有死亡都必须真的经过那个漏斗。只要有一处直接写了 self._alive.discard(x)，后果规则对那条路径就静默失效——不报错、不崩溃，只是那种死法的猎人不开枪。语言本身不强制这件事，Java 的 private 同样不强制（它挡的是类外，而绕过发生在同一个类的兄弟方法里）。

这个项目最终把它做成了结构约束而非纪律：存活集合的类型是 frozenset，discard() 这个方法根本不存在，误写时得到的是 AttributeError 而不是静默旁路；能整体重新绑定它的位置由一条解析源码的测试限定在 _kill 与 reset 之内。两者合起来，等价于 Java 的"不可变视图 + 代码审查"，只是审查是自动的。值得记下的是：这条约束加上去的当天就抓到一处违规，而它出现在项目自己的测试代码里——为了构造一个"已出局的座位"而直接改了存活集合。为省事而绕过漏斗，正是这一设计最容易被破坏的方式。

这里为什么值得这样做

把判断从边上挪到状态上，代价是显式化的状态字段（见上）。这笔交易划不划算，取决于一个问题：

同一类后果，有没有多条路径能触发？本环境中有：六条致死路径对三条后果，且后果之间还能连锁——猎人的枪可以打死另一个猎人。判断挂在边上时代价是乘积，挂在状态上时是求和；后果每增加一条，前者要改六处，后者改一处。反过来，若流程本身是线性的——解析、切片、入库、检索、生成——就不存在需要汇合的多条路径，把判断留在边上不但够用，还能给出一张可以看的图。

这一选择在本环境中付出的具体代价有三项：

代价具体表现
流程不可视没有图。要知道"投完票之后会发生什么"，须读进 step、再进 _settle_if_clear、再进 _next。图编排能直接给出一张图，这在向他人解释系统时是实打实的优势。
状态更厚七个字段纯粹用于记录"接下来该干什么"；它们要在重置时初始化、在重放时被覆盖，改规则时容易漏掉其中一个。
漏斗需要额外的强制手段语言不保证唯一入口，需要 frozenset 加一条解析源码的测试来补。这部分工作在图编排里不存在。

§3信息可见性：权限作为构造，而非检查

上一节的分歧关于控制流。第二处分歧关于信息可见性，而它同样不是实现风格之争——两种做法把权限放在了不同的位置：一种把它做成访问时的判断，另一种把它做成交付时的构造。

视图的三层结构

第二处分歧关于信息可见性，而它的核心是 observe(actor) 返回的那个字典长什么样。它有三层：

view ├── you / role / round / phase … 你自己的基本信息 ├── public 公开层——所有座位拿到的内容完全一样 │ alive、dead、speeches、votes、exiles、sheriff … └── private 私有层——因角色而异 my_actions 人人都有：你自己做过什么 fellow_wolves 只有狼有 checks 只有预言家有 antidote_available 只有女巫有

公开层与私有层的划分本身不新鲜；关键在于这个划分发生在哪一步。它发生在取数时，而不是渲染时。一个村民座位拿到的 private 里只有一个键，一个狼座位拿到的有九个——差异已经体现在数据结构上，而不是留给下游去判断。

渲染层不再承担权限判断

把状态摊给每个节点的设计里，拼提示词的函数承担两件事：先判断"你是谁、你能看什么"，再把结果渲染成文字。两件事交织在一个函数里，而它有全局视角，所以两件事都必须由它做对。

权限判断在渲染层
def build_prompt(state, seat):
    role = state["_roles"][seat]     # 先判断你是谁
    lines = [公共部分]
    if role == "werewolf":           # 再决定给你什么
        lines.append(f"同伴：{找出所有狼}")
    return "\n".join(lines)
权限判断在取数层
def system_message(view, ...):
    priv = view["private"]
    lines = [f"Alive: {view['public']['alive']}"]
    if "fellow_wolves" in priv:      # 有就渲染，没有就跳过
        lines.append(f"同伴：{priv['fellow_wolves']}")
    return "\n".join(lines)

右侧那个条件判断的是字典里有没有这个键，不是"你是不是狼"。"狼才能看到同伴"这条规则完全不在渲染层——它在 observe 里，而它作用的结果就是那个键在不在。渲染层甚至不需要知道游戏里有"狼"这个概念，它只把手上有的东西翻译成文字。

这个拆分之所以要紧，是因为渲染有很多种，权限判断只有一种。同一份视图要被拼成给模型看的提示词、渲染成给真人看的网页、序列化成给观战者的 JSON。三种渲染，三份代码；如果权限判断留在渲染层，就是三处可能写错的地方，而且真人那条路要把整套过滤重做一遍。本项目里没有为真人写过一行过滤代码——真人坐第三个座位，拿到的就是 observe(3)，和模型坐在那里拿到的是同一个字典。这才是"玩家是可替换组件"的实际含义：换一个玩家实现，不需要重新证明隔离。

工具不是第二条信息渠道

智能体除了提示词还有工具（查询历史发言、查询票型等），这看上去像是绕过视图的另一条路。它不是：工具的执行上下文 ToolContext(view, belief, task) 只装了视图和智能体自己的笔记，没有环境对象。工具因此不增加信息，只是分页——历史发言一直在视图的公开层里，只是没有全部铺进提示词（那样太长），需要时用工具翻出来。视图里没有的东西，任何工具都变不出来。

以上三小节说明了这套做法是什么。它并非新技巧：这类做法有名字，也有四十年的先例，而与之相对的另一类做法正是被广泛采用的那一种。

把权限做成检查，是一种做法：调用方来取数据，系统判断"你有没有资格"，然后放行或拒绝。这是访问控制（ACL）的思路，文件系统的读写位、接口上的鉴权中间件都属于此类。把权限做成构造，是另一种：系统交给调用方一个已经受限的对象，调用方对它拥有全部权限，而不该看的东西根本不在这个对象里。这是能力式安全（capability-based security）的思路，Unix 的文件描述符是它最常见的例子——拿到描述符就能读，没拿到则连"读哪个文件"这句话都说不出来。

访问控制

调用方发起访问 → 系统检查「你有权限吗」 → 放行 / 拒绝

权限是行为。每个访问点都需要一次判断，判断本身可能被遗漏、被写错、被绕过。

能力式（本设计）

系统构造一份受限对象 → 交给调用方 → 调用方对它有全部权限

权限是数据。没有访问点，因此没有判断，因此没有可遗漏的判断。

本设计中的 observe(actor) 属于后者：它不判断"这个座位能不能读全场身份"，它构造一个不含全场身份的世界并交出去。座位在那个世界里享有百分之百的权限，因为凡是它不该知道的，都已经不在世界里了。

由此得到的四项性质

其一

没有检查，就没有"忘了检查"。访问控制的每一个检查点都是一处可能遗漏的地方，而检查点的数量随功能增长。这里的检查点是零——不是检查得仔细，是这个动作不存在。本节末记录的那次真实泄露恰是反证：那个接口是访问控制式的（先取全部数据，再想起来应当过滤），所以漏了；修复方式是把它改成能力式，即按可见性构造出该给的那一份。

其二

下游可以做得很笨。世界既已裁剪完毕，消费者就不必理解规则。渲染层那句"字典里有这个键就渲染"正是如此——它不知道游戏里有"狼"这个概念。若采用访问控制，每个消费者都要自己判断一次"这个座位是不是狼"，于是每个消费者都得懂规则，规则也就随消费者数量复制。

其三

发出去的东西可以被检查。视图是数据：可以序列化、可以遍历、可以断言。而"某个检查若被触发是否正确"不是数据，是行为，无法用同样的方式验证。隔离测试之所以能存在，前提就是权限以数据形态存在。

其四

玩家可以由第三方实现。第三方写一个 act(view, task, spec, feedback)，想作弊也没有可作弊的对象。访问控制则需要审查第三方代码有无绕过检查的路径——而这在多智能体基准里几乎是不可能完成的审查。

代价

要为每个参与者构造一份世界。每个回合至少构造一份，观战与网页渲染时还要再构造；构造出的是拷贝，有内存与计算成本。本项目规模下可以忽略，规模更大时需要惰性构造或结构共享，而结构共享又会削弱"拷贝不可被就地修改"这一性质——这是需要权衡的地方，本项目选了简单。

公开信息在各份世界之间重复。同上，可以用共享引用消除，代价同上。

构造函数成为单点。它不防止错误，只是使错误局部化并可被机械检查（见本节末）。

可检查性

需要说清楚的是：这个设计并不能阻止开发者写错。若有人在 observe 里加一行把全场身份塞进视图，泄露照样发生。真正的差别在别处，有两条。

其一，错误只可能出现在一个地方。摊开状态的设计里，任何一个拼提示词的节点都可能泄露，而节点数量随功能增长；这里能决定谁看到什么的只有 observe 这一个函数。审查范围从"所有渲染代码"缩成几十行。

其二，也是更要紧的，泄露的形态从自然语言变成了数据结构。在渲染层泄露，产物是一句话，而且可以是转述的——不必写"三号是狼"，写"你的同伴很可靠"就够了，没有任何自动化手段能检查一段散文是否隐含泄露。在取数层泄露，产物必然是字典里多出的一个键或一个值，而字典是可以遍历、可以断言的。本项目的隔离测试正是这么做的：跑完整局，对每一个回合的每一个座位，把视图序列化后断言其中不出现他人的角色。

这条保证的边界也应当写明。它成立的前提是提示词只由视图派生——渲染函数与玩家的签名里都没有环境对象，因此这条链是闭合的。但它只保证"实现符合设计"，不保证"设计正确"：若规则本身被设计成让村民看到女巫的用药情况，测试照样通过。

更值得记下的是这条保证漏掉的地方会发生什么。本项目一度提供一个读取完整对局记录的接口，它不经过 observe，直接从日志渲染——于是活着的玩家在对局进行中可以读到每一次夜间行动。写这个接口的人（也就是把隔离当作核心卖点、并为此写了整套测试的人）照样漏了，且数日未察觉，因为那套测试检查的是 observe 的输出，而这条路径绕开了它。修复方式是让该接口走同一道门。这件事同时说明两点："记得小心"确实靠不住；而收口的价值不在于让人不犯错，在于犯错之后问题必然属于同一类——某处绕开了那道门——因而定位是分钟级的。

这里为什么值得这样做

构造式的代价是为每个参与者造一份世界（见上）。这笔交易划不划算，取决于一个问题：

参与者之间是否存在信息差，且是否有动机利用它？这是本文全部论证中最具决定性的一条，因为这两个条件各自决定了一件不同的事。

信息差决定了有没有东西要过滤。若所有参与者本就共享同一份信息——多数协作型流水线正是如此——那么"泄露"这个概念不成立，构造式没有任何可省的东西。

动机决定了错误能否被发现。若有信息差而无人有动机利用它，多发出去的字段最坏只是浪费 token：这是效率问题，且随时可以从日志和账单上看出来。一旦存在利用动机，泄露的性质就变了：它不抛异常（多一个键、多一句话都是合法数据）；它的后果与正常表现无法区分（狼精准投出预言家，可能是推理，也可能是看了底牌）；它也读不出来（泄露可以是转述的——不必写"三号是狼"，写"你觉得三号今天有点闪烁"就够了）。这类错误是不可观测的。

而不可观测的错误无法用事后检测来防守。访问控制式的做法本质上是事后检测路线——它假定判断写错了会被发现；构造式是事前排除路线——不该看的东西不在交出去的对象里，"判断错"这个动作不存在。它同时把检查对象从行为换成了数据：不是检查"那个判断有没有写对"，而是遍历发出去的视图断言其中不含他人身份。前者查不了，后者跑一遍就行。

反过来，若场景中不存在信息差，或存在信息差但无人有动机利用，访问控制更省事，构造式纯属多绕一层。

§4公理及其推论

世界状态私有于环境对象，且存在且仅存在一个函数 step(actor, task, action) 能修改它。
智能体持有的一切——观察、动作清单、反馈——都是 step 之外的函数从状态派生出来的副本，不是状态本身。

这句话看上去平庸："状态当然是规则决定的"。但它管的不是"谁决定"，是"谁有资格让世界前进"。

这个项目里真出过一个正好踩线的缺陷。有个函数叫 _chat_speaker()，作用是"现在轮到哪只狼说话"——名字是个查询，实现里却顺手把轮次游标加了一。于是每多调用它一次，讨论就往前推一轮：前端刷新一次页面可能推一轮，重放日志时调用次数与原来不同，重建出来的就不是同一个世界。规则一个字没变，失控的是"什么时候算走了一步"。

公理成立时，observe 调一万次世界纹丝不动，而世界每前进一步都恰好对应日志里的一条 step。一局 12 人局录下来是：读 603 次、问玩家 201 次、写 201 次，日志正好 201 条。

两个维度，同一种构造

§3 说的是"你能看到什么"。同一种构造方式还作用在另一个维度上——"你能做什么"。

认知边界
observe(actor)
  → 你能看到的世界
能力边界
action_space(actor, task)
  → 你能做的动作集

女巫没有解药时，"救人"不是被判为非法——它不在动作清单里。守卫不被允许守护自己时，他自己不在目标名单里。两者与视图遵循同一条原则：不是"你申请、我审批"，而是"我造好交给你，交出去的就是全部"。因此隔离与合法性并非两条独立的性质，而是同一种构造方式分别作用于"知道什么"与"能做什么"的结果。

这也解释了规则参数为什么必须是数据：guard_self 这一个布尔值同时决定目标名单里有没有自己、以及规则文本里那句话怎么写。一条规则，两个出口，同一个源头——一个出口通向能力边界，一个通向认知边界，同源因此不可能互相矛盾。

规则以数据形式存在一处

上一段的 guard_self 说明了一件更一般的事：凡是有两个以上消费者的规则，都必须写成数据。step 读它执行，rules_text 读它渲染给模型看，测试读它构造断言；改数据三处同变，只改引擎不改数据则测试失败。"改了代码忘了改提示词"这类缺陷因此被消掉。

需要说明的是这条约束做到什么程度取决于消费者数量，而非越彻底越好。行为规则有两个消费者（引擎与规则文本），所以抽成了 Variant 的字段；可见性规则只有一个消费者（构造视图那一次），因此留在 observe 的代码里，没有抽成配置表。若哪天要把"狼互相知道身份"写进给模型看的规则文本，它就有了第二个消费者，那时才该抽。抽象过度与抽象不足同样是成本。

确定性

world == f(seed, journal)。世界完全由种子与动作日志决定：中断的对局可以重放接续且重放不询问模型，A/B 实验可以用同一副牌跑两套规则做配对，缺陷可以精确复现到第 N 个回合。这条性质本身直接来自公理——若存在 step 之外的状态写入，日志就不再是完整的输入序列。它与图编排的检查点机制如何取舍，是下一章的内容。

§5持久化：记录状态，还是记录动作

确定性的用途——重放、断点续跑、同种子对照——在图编排框架里也有对应物：检查点（checkpointer）。两者解决同一个问题，做法却相反。这一节把它们并排放好，并说明这个场景为何选了后者。

快照式：图编排的做法

图编排框架在每个超步（super-step，一次调度中所有节点的并行执行）之后写一份检查点。一份检查点里装的是状态本身：通道值（channel_values）、通道版本（channel_versions）与版本可见性记录（versions_seen）；外层还包着线程与检查点标识、元数据、本超步内已完成节点的中间写入（pending_writes），以及指向父检查点的引用。

恢复的语义是：检查点之前的节点被跳过（结果已在快照里），之后的节点重新执行。为容错，超步内单个节点失败时，同超步已成功节点的写入会被保留，恢复时不重跑它们。

日志式：本设计的做法

这里不存状态，只存动作。日志的每一条就三样东西：谁、做什么任务、做了什么。恢复时用同一个种子重新发牌，再把动作依次喂回 step：

def replay(env, seed, journal, upto=None):
    turn = env.reset(seed)                                    # 同种子 → 同样的初始状态
    for rec in journal[:upto]:
        assert (turn.actor, turn.task) == (rec.actor, rec.task), "日志对不上"
        turn = env.step(rec.actor, rec.task, rec.action)       # 动作从日志读，不问模型
    return turn

正常对局时 step 的第三个参数来自模型，重放时来自日志；除此之外走的是同一套规则与结算。世界因此是种子与日志的函数，重放不过是对同一串输入的一次折叠。

不构成差别的部分

两点常被误当作差别，应当先排除。

其一，"恢复时不必重付前缀的代价"两者都做得到。图编排跳过已完成节点，本设计重放时不调用模型，在省钱这一点上没有分别。

其二，两者都支持中途接管。人工介入、从中间某点继续，都不是任何一方独有。

四处真正的差别

其一 · 存下来的东西有没有意义

日志是 (谁, 做什么, 做了什么) 的序列，它同时就是这局对局的记录本身：统计兜底率、做同种子配对、审计某个模型在第几回合做了什么判断，用的都是它。快照存的是运行时内部表示，能恢复执行，但不能直接回答"这局发生了什么"。

其二 · 体积与增长

快照每个超步一份，长线程上会持续增长；官方文档为此提供了增量通道（DeltaChannel），只存增量以压缩体积。日志每回合一行，而那一行本就是模型返回的 JSON——它天然可序列化，不需要额外的序列化约定。

其三 · 失效时的表现

两者都会因"被恢复的东西与当前代码不匹配"而失效：快照绑定图结构与通道版本，日志绑定规则。差别在于失效如何暴露。日志式重放每一步都断言"环境认为该谁行动"与"日志记录的是谁"一致，不一致当场停下并指出第几步分叉；它不会悄悄重建出一个不同的世界。

其四 · 重放会不会重新产生副作用

图编排的文档明确指出：中断在重放时总会被重新触发，若配置了人工审批，恢复时需要重新审批一次。这是快照式的固有性质——检查点之后的节点要重新执行，那么这些节点的副作用也会重新发生。日志式重放不重新执行任何外部动作，因为动作的结果已经在日志里；重放只是把它们重新应用到状态上。

代价：日志式要求确定性，快照式不要求

这是快照式实打实的优势，必须写明。快照记录的是"状态成了什么样"，因此节点内部是否确定无关紧要——调了外部服务、用了时间戳、模型温度不为零，快照照样存得住、恢复得了。日志式记录的是"做了什么"，要从它重建状态，就必须保证同样的动作作用在同样的状态上得到同样的结果；任何非确定性的来源都不能进入状态转移。

另有一处量级上的取舍：日志式恢复是重新计算，代价随步数增长；快照式是反序列化，代价随状态大小增长。步数多而状态小的系统，日志式吃亏。本环境每局约二百回合、状态数十个字段，重放一百多个回合耗时不足一秒，因此这一项不构成约束。

这里为什么选日志式

其一，产出要当数据用。这个环境的目的不是打完一局，而是产出可统计的记录。日志既是存档又是记录，两者本来就是同一份东西；若采用快照，仍需另外维护一份对局记录，于是又出现了两个必须保持一致的来源——正是 §1 所述的那类问题。

其二，要审计的是过程而非结果。"这个模型在第 137 回合做了什么判断、依据是什么"，快照答不了，它只说得出那一刻状态是什么样；日志逐条记着谁做了什么，配合每步的推理字段可以直接读。

其三，确定性在这里是本来就要的东西。日志式的前提（转移必须确定）对本设计不是额外负担——公理已经把状态写入收敛到 step 一处，而规则本身不依赖时间与外部服务。前提免费，代价便只剩重算，而重算在这个规模下可以忽略。

反过来，若节点会调用外部服务、状态里存着不可重现的东西，或者流程只需恢复执行而不需被审计，快照式是更合适的选择——它不要求你放弃非确定性。

§6三处与常规做法相反的取舍

身份是编号，行动能力是对象

环境里的一切都用座位号称呼参与者，而"能做出动作的那个东西"是另一个对象，由驱动循环用编号去查表拿到。直觉上应该合并成一个玩家对象——但一旦合并，环境就持有了智能体的引用，"环境只通过 observe 供给信息"这条就没有了强制力。分开的代价是多一次查表，换来的是隔离从约定变成结构。

step 返回下一个轮到谁

更常见的写法是把"下一步是谁"做成独立方法。但刚改完状态的那个函数最清楚下一个是谁；拆出去就等于让"下一步"有了第二个来源，两个函数读同一份状态各推一遍，迟早分叉。代价是 step 的职责变重，收益是控制流只有一处。框架因此不知道"投完票就到晚上"——它只是把 step 返回的东西喂回循环。

非法动作作为对话的一部分

模型给出非法动作时，校验返回的是理由字符串，这个理由回灌给模型让它重试。三次仍不合法才使用环境定义的兜底动作，并标记该回合。标记是必须的：兜底动作本身合法，不标记的话日志就把系统代打记成了模型的判断，之后基于日志的一切分析都建立在假数据上。

§7有意省略的部分

没有理由
图 / DAG控制流由状态决定，不是预先声明的。声明一份就等于给"下一步"加了第二个来源。
检索式记忆单局上下文长度可控，历史发言可由工具按需查询。引入向量检索会在评测里多一个不可控变量。
沙箱工具全部是对本局状态的纯查询，不触碰外部世界。没有需要隔离的副作用。
运行时的通用能力Layer A 不含重试策略、不含日志格式、不含并发模型。这些是使用者的选择，写进框架就成了所有人的约束。

§8为什么以狼人杀为载体

前面各节论证的是设计本身。但一套设计只能在它被检验过的场景里被相信，因此有必要说明：这个载体是怎么来的，它压到了哪些地方，又有哪些地方它压不到。

它不是被挑出来的，是起点

诚实地说，这里没有"先确定研究问题、再挑选合适基准"的过程。项目最初就是一个狼人杀对局程序；本文所述的这层契约，是在那个程序变得难以维护之后从中抽出来的——引擎一份规则、提示词一份规则、校验一份规则，三份各自演化，于是才有了§1 的问题陈述。论证的顺序与发生的顺序相反，这一点不应当被叙述掩盖。

但这不妨碍事后判断它是否合适。§2、§3 与 §5 各自记录了三处选择在这个场景下为何值得；此处补充两点便利，以及它检验不到的地方。

两点便利

真人可以坐进去。这是检验"玩家是可替换组件"最直接的方式：一个人坐进第三个座位，收到的必须与模型收到的完全一致，否则要么泄露、要么不公平。这条约束若不成立，隔离就只是纸面性质。

领域知识为零。规则是常识，读者不需要背景就能判断"这个座位不该看到那个信息"是否成立。换成供应链博弈或金融撮合，论证同样成立，但读者要先学一套领域术语才能验证它。

它检验不到的地方

把边界写清楚，否则前面的结论会被读成比实际更强的东西。

未被检验原因
沙箱与副作用隔离本环境的全部工具都是对本局状态的纯查询，不触碰外部世界。真实智能体系统里的工具会写数据库、发请求、花钱，那类隔离本设计一行未写。
长程记忆与上下文压缩单局上下文长度可控，历史发言按需检索即可。需要跨会话记忆的场景，这里没有任何证据。
分布式与并发一致性一局一个线程，状态在进程内。多进程共享一个环境时公理如何维持，本设计未做回答。
规模最大十五个座位、每局约二百回合。参与者数量再高一个量级时，"为每个人构造一份世界"的开销是否仍可接受，未经验证。

换言之，本文的结论限于回合制、进程内、参与者数量在十几量级、工具无副作用的对抗环境。超出这个范围的部分，本项目没有提供证据。

§9两项已被推翻的论断

把这一节写进来，是因为设计过程里最有价值的部分往往是被否掉的那些。

收回其一 · 论证方式

最初为"隔离必须由框架保证"给出的理由是：有人可能写错——某个提示词拼装函数为省事直接读取了全场身份。

不认可，你不能假设有人写错，只要框架本身可以保证狼人看不到不该看的东西即可了。—— 项目过程中的原话

这个反对是对的，而且比原来的理由更强。"怕人写错"是概率论证，靠的是纪律；"结构上不给机会"是构造论证，靠的是类型和可见性。observe 返回副本、状态私有、玩家拿不到环境引用——这三件事一起使得想泄露也没有渠道。公理的最终形式来自这次反对。

收回其二 · 一个多余的分类

曾把规则分成两类：参数型（能触发开枪的死因集合、投票能否弃权）写成结构化数据，逻辑型（同守同救不抵消、平票无人出局）只能是代码。并据此设计了两套处理方式。

我没懂的地方是，现在无非是要不要把句子写死……所以我没懂这里分成两种的意义在哪。—— 项目过程中的原话

确实没有意义。两类规则要的是同一件事：只写一遍，三处引用。参数型引用的是数据结构，逻辑型引用的是同一个函数——差别只在被引用的东西长什么样，不构成两种设计。这个分类被删掉，关于规则数据的那一节从两段合并成一句。

顺带删掉的还有一个自造词。原先把"从规则数据构造断言的测试"叫作探针测试，被指出这就是普通测试，没必要造名词。造词会让读者以为有新机制，是纯粹的损耗。

§10契约层的规模

两项与机制无关的代价

以上各章分别记录了每处选择自身的代价。还有两项与具体机制无关，属于自研运行时的固有成本。

没有生态。检查点、链路追踪、可视化调试器，全部自行实现。

无人认识它。三百五十八行是自己的三百五十八行：新人要读完才能改，而某个通用框架的新人可能已经会了。这一条在真实团队中往往权重最高，也最容易在技术论证中被忽略——若团队已在使用某个编排框架、而场景又属于协作型，直接沿用它是更好的选择。

Layer A 是 358 行：环境暴露五个方法，玩家暴露一个方法，step 的返回是"下一个轮到谁"或"结束了"的联合类型。整个驱动循环是十七行。

薄本身不是目的，可验证才是。一层薄到能被完整覆盖的契约，才能说"隔离由框架保证"而不是"由使用者遵守"。换一个对抗场景——拍卖、谈判、多方博弈——重写的是规则层；这十七行不动。

这也是它与编排框架的分工：编排框架解决"多个步骤怎么串起来"，这层解决"多个参与者对同一个世界的认知怎么受控地分发"。前者的答案是图，后者的答案是一条公理和四条从它推出来的性质。

同一局，两种存法

真实的一局八人局，逐步录下来。左边是快照式：每走一步就把整个世界重存一份，着色的是这一步真正变了的字段。右边是日志式：每走一步只追加一行。往后点，看两边分别长成什么样。
